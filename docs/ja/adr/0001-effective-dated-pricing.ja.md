# ADR-0001: 適用開始日つき単価 — 各レコードは、その呼び出し時点で有効だった単価で計算する

| 項目 | 値 |
|-------|-------|
| Status | Accepted |
| Date | 2026-09-29 |
| Binds | gem-usage-lens |
| Decision makers | nlink-jp maintainers |
| Triggered by | Vertex AI の料金ページが Gemini 3.8 / 3.7 / 3.6 Flash に 2027-01-01 開始の 2 つ目の単価を掲載した。モデルごとに単価 1 組の表では両方を表せず、新単価を後から足すと `reprice` が 2026 年分を書き換えてしまう |

## 背景

単価表（`core/pricing`）はモデルごとに単価を **1 組** しか持たない。価格計算の
経路はすべて、呼び出しがいつ行われたかに関係なく、その 1 組を全レコードに当てる。
`ingest` は新しいレコードをその単価で計算し、`reprice` は **蓄積済みの全レコード**
をトークン列からその単価で再計算する。

Vertex AI の料金ページ（Gemini 3 節、2026-09-29 確認）は、利用中の 3 モデルを
2 行に分けている。

| モデル | 2026-12-31 まで | 2027-01-01 から |
|---|---|---|
| gemini-3.8-flash / 3.7-flash / 3.6-flash | 入力 $0.75 / 出力 $3.75 / キャッシュ $0.075 | 入力 $1.50 / 出力 $7.50 / キャッシュ $0.15 |

non-global の行はそれぞれの 1.1×、キャッシュ読み取りの比率は 0.1× のまま。
ページは現行単価を "introductory pricing … through December 31, 2026" と呼び、
その後は "standard pricing … will apply" としている。

モデルごとに単価が 1 組では、表は 2026 年か 2027 年のどちらかにしか正しくなれない。

- **表を変えない** → 2027-01-01 以降の呼び出しはすべて定価の半額で記録され、
  月予算は 1 月から過少計上になる。
- **1 月に表を更新する** → 新しい呼び出しは正しくなるが、次の `reprice` が
  2026 年全体を新単価で再計算し、倍額にする。`reprice` は他のあらゆる単価誤りの
  文書化された修正手段である（グラウンディング料金を 1,000 クエリあたり $35 から
  $14 に直したのもこれ）。したがってこれは例外ケースではなく通常の経路である。

**記録済みの教訓は「予定価格を書くな」と言っており、それは維持する。** knowledge の
`llm-integration.md`（「単価表の同期では…」）は、表に未来の予定を書かず、
検証日を記録し、次の同期で予定が実現したかを確認せよと言う。この教訓は、日付つきの
導入価格の値上げ予定が撤回された事例から来ている（Claude Sonnet 5: 2026-09-01
予定だった $3 / $15 は実施されなかった）。今回の 2027 年の行も同じ種類 —
導入価格の日付つきの終了 — である。教訓は「何を書くか」については正しいが、平らな
表を前提にしていた。予定された変更が実際に起きたとき、今の表ではそれを記録する方法が
旧単価の上書きしかなく、次の `reprice` が履歴を書き換える。この ADR は、教訓に
従える表を用意する。

開始日には料金ページ上でタイムゾーンが書かれていない。Cloud Billing の Reports の
文書は次のように言う: "A 24-hour time period in the Cloud Billing report starts
at midnight US and Canadian Pacific Time (UTC-8), and observes daylight saving
time shifts in the United States." これはレポートが日をどう区切るかの説明で
あって、価格変更がいつ効くかの説明ではない。Google が課金について文書化している
日の区切りとしては、これが最も近い。

## 決定

1. **モデルの単価は期間の列にし、各期間に適用開始の瞬間を持たせる。**
   各モデルは `From` の昇順に並んだ期間を持つ。最初の期間は始まりが開いている
   （全モデルについて表のテストで強制する）。`Lookup(model, at)` は `From` が
   `at` 以前である最後の期間を返す — `From` ちょうどのレコードは新単価になる。
   `Known(model)` は時刻なしで「このモデルに単価があるか」に答え、`ingest` /
   `reprice` の未知モデル警告に使う（`unpriced_*` は保存済みの金額を読み、単価表は
   参照しない）。store は `ts` を秒単位で持つので、`From` はすべて整数秒で
   なければならない。そうすれば ingest（完全精度の時刻）と `reprice`（保存された
   秒）が必ず同じ期間を選ぶ。

2. **価格計算のすべての経路はレコード自身の時刻を使う。** `ingest` と `reprice`
   は各レコードをその時刻で計算する。`repriceSelect` は `COALESCE(ts, 0)` を読む。
   時刻の無いレコード（作者の store には無い: 2,830 行中 0 件）は最初の期間に
   入る。結果は決定的で、`reprice` を実行した時点に依存しない。

3. **組み込み表には引き続き有効な単価だけを書き、変更は実施された後に新しい期間
   として足す。** 記録済みの教訓は維持する: 予定価格は撤回されたり恒久化されたり
   しうるので、先回りして書かない。開始日の後の最初の同期で変更が確認できたら、
   新単価を**その適用開始の瞬間から始まる期間として追加する** — 旧単価の上に
   上書きはしない — そのうえで `reprice` が境界以降に作られたレコードを直し、
   それより前のレコードはそのまま残す。この規則は表のテストで固定する: 組み込みの
   期間はどれも `VerifiedOn` より後に始まらない。knowledge の教訓には、同じ変更で
   後半 — 変更が実施されたときにどう記録するか — を書き足す（決定 8）。

4. **期間は適用開始日の米国太平洋時間の午前 0 時に始まる**とし、オフセットつきの
   RFC 3339 の瞬間を文字どおり書く — 2027 年の変更なら
   `2027-01-01T00:00:00-08:00`（`08:00Z`、日本時間 17:00）。
   `time.LoadLocation` で計算はしない。Windows と Linux のビルドは zoneinfo を
   埋め込まない限りそれに頼れない。1 月は PST（−08:00）で、夏の境界なら −07:00
   になるので、瞬間は導出せず 1 つずつ書く。

5. **config の上書きはそのモデルの全期間に、フィールドごとに効く。**
   `[pricing.models."<id>"]` は平らなまま。上書きしたフィールドは各期間のその
   フィールドを置き換え（交渉済み単価は全日付で定価を置き換える）、省略した
   フィールドは各期間の値を保つ。config では日付を表せない。予定を持つモデルで
   `input_per_mtok` / `output_per_mtok` を上書きすると予定された変更が平らに
   潰れるので、`models` と `doctor` はそれをモデル名つきで知らせる。
   `config.example.toml` の「価格改定後」の例（2027 年の単価を 2026 年にも押し
   付けてしまう）は書き直す。スナップショット別名（`gemini-3.7-flash-001`）の
   config キーは独立した単一期間のエントリであり、元モデルの予定は継承しない —
   文書に書き、単価が変わるモデルを覆い隠すそのようなキーは `models` / `doctor` が
   名指しする。

6. **表示面。**
   - `models` は期間ごとに 1 行を、`FROM` 列（開いた最初の期間は `—`）つきで
     表示し、現在有効な期間に印をつける。
   - `models --json` は `models` を今のまま保つ — モデル → **現在有効な**単価、
     フィールドも同じ — うえで `schedule` を追加する: モデル → 全期間を
     `{"from": "<RFC 3339>" | "", …単価}` で。常に書く（`omitempty` なし、開いた
     最初の期間は `""` — このリポの「無い瞬間」の慣習）。テストで両キーを固定する。
     「現在」はテスト用に注入する。
   - `ingest` / `reprice` の未知モデル警告は `Known` を使い、`unpriced_*` は保存
     済みの $0 行を数える。どちらも時刻に依存しない。
   - `budget` と `report` は保存された `cost_usd` を合計するので変更なし。
   - `verify` は価格計算をしないので変更なし。

7. **いまは何も reprice せず、仕組みは変更より前に出荷する。** いま期間は
   足さないので、保存済みの金額は動かない。このリリース（CLI と、それを同梱した
   GUI）は、1 月の同期を「期間を 1 つ足して `reprice`」で済ませるためのもので
   ある。2027-01-01 からその同期が出荷されるまで、3 モデルのレコードは 2026 年の
   単価で計算される — 許容する過少計上であり（「結果」を参照）、同期後の
   `reprice` が正確に直す。1 月のリリースには GUI のリリースも含める: GUI は
   **同梱** CLI で毎分取り込み、Reprice ボタンもその CLI を実行する。`daemon` の
   launchd ジョブも新しいバイナリを指すようにする。

8. **単価変更の記録方法を、規則が読まれるすべての場所に同じ変更の中で書く**:
   `core/pricing/table.go` の `VerifiedOn` コメント、AGENTS.md の
   "no scheduled future prices" の注意書き（維持し、期間を足す手順を加える）と
   Structure の行、README / README.ja（「単価」: 日付ごとの規則と `FROM` 列）、
   `config.example.toml`、knowledge の `llm-integration.md`（ja + en）、
   プロジェクトの memory（2027 年の同期が残っていることも記録する）。

## 結果

- モデルごとの平らなエントリが期間の表に置き換わる。単価が 1 つのモデルは従来
  どおり読める。`Table` の形は変わるが、このモジュール内部のものである。GUI が
  読むのは `report` / `budget` の JSON だけで（ソースの grep で確認）、`models`
  JSON のキーは形を保つ。
- 必要なテスト（組み込み表にはまだ複数期間のモデルが無いので、複数期間の挙動は
  合成の表で確かめる）: `-08:00` の境界での `07:59:59Z`・`08:00:00Z`・
  `08:00:01Z` の `Lookup`、`-07:00` の境界でも同じ。組み込みの期間がどれも
  `VerifiedOn` より後に始まらないこと。全モデルで最初の期間が開いていること。すべての
  `From` が整数秒であること。config の上書きが全期間に入り、省略したフィールドは
  各期間の値を保つこと。日付が混在した store の `reprice` が 2026 年の行を変えず
  2027 年の行を新単価にすること。ingest の後の `reprice` が境界の両側で 0 件しか
  変えないこと。`models --json` の形（両キー）。
- **許容: 同期が出荷されるまで 1 月は過少計上になる**（決定 3）。2027-01-01
  から、新しい期間が CLI と GUI の両方でリリースされるまで、3 モデルは定価の半額
  で記録され、月予算も低く出る。その後の `reprice` が影響したレコードをすべて直す。
  残っている同期はプロジェクトの memory に記録し、成り行きに任せない。
- **許容: 境界の瞬間は推定である。** Vertex が 2027-01-01 の別の瞬間に新単価を
  適用した場合、その幅（UTC 午前 0 時から最大 8 時間、日本時間午前 0 時から
  17 時間）の呼び出しは反対側の単価になる。作者の現在の利用量では 1 ドル未満。
- **許容: 古いバイナリは修正を打ち消しうる。** 2027 年の期間を持たないビルドの
  ままの GUI や CLI が境界後に取り込みや `reprice` を行うと、2026 年の単価を
  書き戻す。後で新ビルドの `reprice` を実行すれば戻る。
- `claude-usage-lens` も単価 1 組の同じ構造だが、現在予定された変更は無い。この
  ADR は gem-usage-lens だけを拘束する。

## 検討した代替案

- **A. 単価は 1 組のまま、当日に表を更新し、以後 `reprice` しない。** ツール自身
  が単価修正のたびに実行せよと案内するコマンドを、誰も実行しない間しか正しくない。
  更新されないインストールも過少計上になる。
- **B. ある日付より古い保存済み金額を凍結する。** 単価誤りの修正手段としての
  `reprice` を失う。すでに必要になった実績がある。
- **C. 各レコードに単価のスナップショットを保存する。** スキーマ変更であり、正しく
  計算するにはやはり日付つき単価が要る。しかも修正した単価を履歴に適用できなくなる。
- **D. 日付つき期間は config のみ（組み込みは平らのまま）。** 公表済みの日付つきの
  事実を、利用者全員に書き写させることになる。必要が出れば config の期間は後から
  足せる。本決定はそれを妨げない。
- **E. UTC またはローカル時刻の境界。** どちらも Google は課金について文書化して
  いない。太平洋時間の境界が、文書化されている最も近いものである。
- **F. 公表済みの 2027 年単価をいま組み込み表に書く。** 1 月は自動で切り替わり、
  予算モニタにとっては（変更が撤回された場合の）過大計上のほうが過少計上より安全な
  方向である。記録済みの教訓を維持するというメンテナの判断で却下: 日付つきの導入
  価格は過去に撤回されたことがあり、有効な単価だけを載せる表こそ、読み手が料金
  ページを見直さずに信用できる表である。これにより 1 月に残る過少計上は同期で
  区切られ、`reprice` で元に戻る。
